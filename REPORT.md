## 1. Цель работы

Научиться воспроизводимо подготавливать табличные данные, сохранять и переключать их версии, работать с ветвлением и слиянием в Git/DVC, восстанавливать данные из отдельного DVC remote, а также создавать и проверять версии ClearML Dataset с помощью Dataset ID и графа зависимостей.

## 3. Подготовка данных

Для работы использованы встроенные в scikit-learn наборы `load_iris(as_frame=True)` и `load_wine(as_frame=True)`. CSV создаются без индекса pandas, с детерминированной сортировкой по исходным признакам и целевой переменной.

Скрипт `prepare_data.py` поддерживает три режима:

- `base` — создаёт исходный `data/iris.csv`;
- `wine` — создаёт `data/wine.csv`, не изменяя Iris;
- `iris_features` — добавляет в Iris два вычисляемых признака:
  - `sepal_area = sepal length (cm) × sepal width (cm)`;
  - `petal_area = petal length (cm) × petal width (cm)`.

Скрипт `check_data.py` проверяет наличие ожидаемых файлов, SHA-256, форму таблиц, названия столбцов, пропущенные значения, отсутствие безымянного индекса и корректность вычисляемых признаков.

### Итоговые таблицы

| Состояние | Файл | Размер | Столбцы |
|---|---|---:|---|
| Базовый Iris | `iris.csv` | 150 × 5 | `sepal length (cm)`, `sepal width (cm)`, `petal length (cm)`, `petal width (cm)`, `target` |
| Iris с признаками | `iris.csv` | 150 × 7 | исходные 5 столбцов + `sepal_area`, `petal_area` |
| Wine | `wine.csv` | 178 × 14 | `alcohol`, `malic_acid`, `ash`, `alcalinity_of_ash`, `magnesium`, `total_phenols`, `flavanoids`, `nonflavanoid_phenols`, `proanthocyanins`, `color_intensity`, `hue`, `od280/od315_of_diluted_wines`, `proline`, `target` |

## 5. DVC

### 5.1. Метаданные и remote

Git хранит `data.dvc`, который описывает состояние каталога `data`. Самих CSV в Git нет.

| Параметр | Значение |
|---|---|
| Путь, описанный в `data.dvc` | `data` |
| DVC output hash | `6824bfe7cc9a875ae258ae7d6c627f74.dir` |
| Размер output | 18 170 байт |
| Число файлов | 2 |
| Локальный DVC remote | `../../dvc-storage` |

Remote расположен вне сдаваемого репозитория. Команда `dvc push` отправила объекты данных в remote.

> **Хэши DVC:**
- SHA-256 файла `data.dvc`: `3c73bfb7df23ff34141d6d3896421c55e6b75ff7f603fba77a3dd0681cbd81c2`.
- DVC output hash каталога `data`: `6824bfe7cc9a875ae258ae7d6c627f74.dir`.

Это разные значения: SHA-256 вычислен для самого файла метаданных `data.dvc`, а DVC output hash идентифицирует содержимое каталога данных.

### 5.3. Слияние и восстановление

В `feature/iris-features` была объединена ветка `feature/wine`. Итоговая версия содержит оба CSV, при этом Iris сохраняет вычисляемые признаки. После слияния были проверены данные, а итоговые объекты отправлены в DVC remote.

Затем репозиторий был клонирован в отдельную директорию `mlops-data-bychkova-clean`, данные восстановлены через `dvc pull`, после чего `check_data.py` прошёл проверку. Это подтверждает, что итоговые файлы можно получить не только из исходной рабочей директории.

Последняя проверка DVC в основном рабочем репозитории: `dvc status` → `Data and pipelines are up to date.`

## 7. Сравнение DVC и ClearML Dataset

| Критерий | DVC | ClearML Dataset | Наблюдение в этой работе |
|---|---|---|---|
| Идентификатор версии | Git-коммит + DVC-метаданные и хэш данных | Dataset ID и номер версии | Для DVC сохранена история Git; для ClearML зафиксированы три корректных ID |
| Расположение метаданных | `.dvc`-файлы в Git | ClearML Server | `data.dvc` хранится в репозитории; lineage проверен через SDK |
| Хранение файлов | Workspace, DVC cache, DVC remote | ClearML storage и локальная копия | DVC remote — `../../dvc-storage`; версии ClearML скачивались по ID |
| Создание дочерней версии | Изменить данные, обновить DVC-метаданные и сделать Git-коммит | Создать Dataset с parent ID, добавить изменения, загрузить и финализировать | В Git использованы отдельные ветки; в ClearML указаны родители |
| Переключение версии | `git switch` и `dvc checkout`; при отсутствии объектов — `dvc pull` | Получить нужный Dataset по ID | DVC-состояние восстановлено из метаданных; ClearML-версии проверены по ID |
| Восстановление на чистой машине | Клонировать Git и выполнить `dvc pull` | Скачать Dataset по ID при доступе к ClearML storage | Чистый clone DVC восстановил оба итоговых CSV |
| Ветвление | Git-ветки с разными состояниями `.dvc` | Дочерние Dataset с общим parent | `feature/wine` и `feature/iris-features`; в ClearML обе версии имеют общий базовый parent |
| Слияние | Git merge с DVC merge driver и проверкой данных | Lineage показывает родителей; результат фиксируется отдельным Dataset | DVC-ветки объединены и итоговые CSV проверены |
| Связь с Git | История версий данных связана с Git-коммитами | Dataset существует отдельно от Git | Git содержит `data.dvc`, а ClearML ID сохранены в отчёте |
| UI | Git UI показывает историю; для данных нужен DVC remote | ClearML UI показывает версии и зависимости | Для ClearML проверялись ID и граф зависимостей |

## 8. Ответы на контрольные вопросы

### 1. Какой объект однозначно определяет версию данных в DVC?

Версию определяет состояние DVC-метаданных в конкретном Git-коммите вместе с хэшем данных, на который ссылается `.dvc`-файл. Для восстановления также необходим доступ к соответствующим объектам в DVC cache или remote.

### 2. Почему одного Git-коммита недостаточно без DVC remote?

Git хранит код и DVC-метаданные, но не сами CSV. Если нужных объектов нет в локальном cache и они недоступны в remote, одного Git-коммита недостаточно для восстановления содержимого данных.

### 3. Чем Dataset version отличается от Dataset ID в ClearML?

Dataset version — человекочитаемый номер, например `1.1.0`. Dataset ID — уникальный идентификатор конкретного объекта версии. В работе версии получались через `Dataset.get(dataset_id=...)`.

### 4. Почему `finalize()` нельзя считать созданием следующей версии?

`finalize()` завершает текущий Dataset и фиксирует его состояние. Для следующей версии нужно отдельно создать новый Dataset с новым номером и корректным parent ID.

### 5. Как доказать, что ClearML version `2.0.0` создана от базы, а не от `1.1.0`?

Нужно проверить parent ID или dependency graph. В фактически корректной версии `2.0.1` parent равен ID базовой версии `1.0.1` — `2c15801472e0431a901bfe6c4fe0c581`. ID Wine-версии `5cdf5d16eb0e4b018a11019bffe5a139` не является её parent. Фактическая корректная версия называется `2.0.1`, а не `2.0.0`.

### 6. Что произойдёт, если после `git switch` не выполнить DVC checkout?

Git переключит версию DVC-метаданных, но файлы в workspace могут остаться от предыдущей ветки. Код и данные окажутся несогласованы. `dvc checkout` восстанавливает состояние по текущим метаданным из cache; если объектов нет, их нужно получить через `dvc pull`.

### 7. В каком сценарии этой работы удобнее DVC, а в каком ClearML Dataset?

DVC удобен для версионирования данных вместе с Git-ветками, коммитами, слияниями и восстановления проекта из репозитория и remote. ClearML Dataset удобен для получения конкретного набора по Dataset ID, просмотра родительских версий и lineage в интерфейсе ClearML.
